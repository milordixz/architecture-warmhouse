# Экосистема «Тёплый дом»

## Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи удалённо управлять отоплением в своём доме (нет в коде, но в описании лаб. работы есть)
- Система поддерживает выполнение запросов к установленным датчикам в системе отопления
- Для подключения нового дома требуется выезд специалиста.
- Самостоятельное подключение датчиков и реле пользователем не поддерживается.

**Мониторинг температуры:**
- Можно получить данные по датчикам
    - Получить температуру по датчику
    - Получить температуру по всем датчикам, которые завели
    - Получить температуру по датчиками в локации

**Управление датчиками**
- Создать датчик
- Обновить данные датчика
- Обновленных полученных значений по датчику
- Удаление датчика

P.s Веб интерфейса для клиента нет (нет в коде, но в описании лаб. работы есть), только данные в JSON (представлю что он есть хД)

### 2. Анализ архитектуры монолитного приложения

- Архитектура: монолитная. Обработка HTTP-запросов, бизнес-логика и работа с данными выполняются в одном приложении.
- Взаимодействие: синхронное. Сервер последовательно обращается к базе данных и датчикам.
- В системе нет микросервисов, брокера сообщений, асинхронных вызовов и реактивного взаимодействия, как и кешей.
- Нет графического администрирования устройств, отдельного SPA приложения
- Масштабирование ограничено: нельзя независимо увеличить только нагрузочные части системы.

### 3. Определение доменов и границы контекстов

**Контекст управления устройствами** отвечает за регистрацию устройств, их типы, подключение и текущее состояние.
Он скрывает различия между устройствами компании и устройств партнёров.

**Контекст мониторинга температуры** отвечает за получение, нормализацию и отображение показаний датчиков.
Он публикует события телеметрии для других частей системы.

**Контекст управления отоплением** отвечает за состояние отопления дома и отправку команд реле.
Он не должен владеть данными телеметрии.


### **4. Проблемы монолитного решения**

- Изменение одного функционального блока требует изменения и развёртывания всего приложения.
- Масштабирование бэкенда только целиком, можно подключить HA proxy, для балансировки, а вот база данных не готова
- Единая база данных усиливает связанность модулей и усложняет независимое развитие доменов.
- Синхронный опрос датчиков увеличивает время ответа и связывает доступность системы с доступностью каждого устройства.
- Подключение нового типа устройства требует изменений в центральном приложении.
- Пользователь не может самостоятельно добавить устройство и настроить сценарий.
- Отсутствуют асинхронная доставка телеметрии, повторная обработка сообщений и буферизация временно недоступных устройств.

## Задание 2. Проектирование микросервисной архитектуры
На основе анализа направления, выделена такая архитектура.

Целевая экосистема состоит из API-шлюза, сервиса домов и локаций, универсального сервиса управления устройствами,
собственного IoT-шлюза компании (так как все упирается в протокол взаимодействий устройств, а это zigbee,
zwave) и двух брокеров сообщений. В облачной платформе, сервисы владеют своими данными: сервис домов хранит дома,
участников и привязки, а сервис устройств — устройства, шлюзы.

Пользователь создаёт дом и привязывает к нему шлюз и устройства через облачную платформу из своего аккаунта.
После проверки привязок шлюз получает provisioning-конфигурацию, MQTT endpoint, credentials и ACL. Отопление,
освещение и ворота моделируются как устройства, а их поведение определяется метаданными типа устройства: категорией,
protocol, capabilities и схемами команд и телеметрии. События об обнаружении устройств, телеметрии и изменении
состояния передаются через брокеры сообщений.

Внутренний брокер событий платформы на Kafka/RabbitMQ используется для обмена нормализованными событиями между
микросервисами. Отдельный MQTT-брокер IoT на HiveMQ обслуживает подключения домашних шлюзов,
передачу команд и приём сырых показаний. MQTT-брокер не заменяет внутренний брокер событий.

API-шлюз, MQTT-брокер, STUN-сервер и TURN-сервер находятся в публичном контуре платформы. API-шлюз принимает
HTTPS-запросы клиентов, MQTT-брокер принимает защищённые MQTT-соединения домашних шлюзов (по которым получается данные
от устройств или дает им команды), STUN помогает определить внешние адреса для WebRTC, а TURN ретранслирует медиаданные
при невозможности прямого соединения через NAT. Доступ к этим точкам контролируется аутентификацией, TLS и
правами доступа. STUN и TURN могут быть реализованы одним deployment на базе coturn.

Видеонаблюдение выделено в отдельный контур. Камеры подключаются к домашнему видео-шлюзу через RTSP,
ONVIF или протокол производителя. Видео-шлюз устанавливает исходящее защищённое соединение с медиасервисом
Медиасервис использует WebRTC, STUN/TURN и сохраняет снимки и записи в объектное хранилище.
MQTT используется только для команд и событий, но не для передачи видеопотока.

Теплосчётчики подключаются к домашнему IoT-шлюзу через адаптеры `Pulse`, `M-Bus` или `RS-485/Modbus`.
Адаптер считывает импульсы или регистры на edge-уровне, хранит накопленный счётчик и буферизует показания
при отсутствии связи. В облако передаются нормализованные накопленные значения с единицей измерения,
временем, номером последовательности и признаком качества через событие `MeterReadingRecorded`.
Сервис телеметрии получает метаданные устройства и применяет коэффициент импульса или карту регистров,
поэтому отдельный сервис отопления для счётчиков не требуется.

## Задание 4. Создание и документирование API

### 1. Тип API

Для синхронных запросов используется REST API поверх HTTPS/JSON. API-шлюз
является единой публичной точкой входа и маршрутизирует запросы к сервису
домов и локаций, управлению устройствами, телеметрии, автоматизации и
видеонаблюдению. REST подходит для операций, которым нужен немедленный ответ:
создание дома, регистрация устройства, проверка прав, получение истории
телеметрии и создание WebRTC-сессии.

Для событий и команд используется асинхронный обмен сообщениями. MQTT over TLS
применяется только между облачной платформой и домашними IoT-шлюзами: через
него передаются команды, состояния и сырые показания. Kafka/RabbitMQ используется
как внутренний брокер платформы для событий. Асинхронный обмен позволяет
буферизовать сообщения на шлюзе, повторять обработку и не блокировать клиента
на время выполнения команды.

### 2. Документация API

- [OpenAPI: публичный REST API-шлюз](docs/api/openapi.yaml)
- [AsyncAPI: MQTT-события шлюзов и устройств от него](docs/api/asyncapi.yaml)

OpenAPI описывает синхронные операции домов, привязок, устройств, команд,
телеметрии, сценариев и видеосессий.

AsyncAPI описывает только MQTT-топики домашних шлюзов: команды, состояния,
показания и обнаружение устройств.

# Задание 5. Работа с docker и docker-compose

В каталоге `apps` находится запускаемый учебный пример монолита управления датчиками и отдельный сервис `temperature-api`.

Запуск:

```bash
cd apps
docker compose down -v
docker compose up --build
```

Монолит доступен по адресу `http://localhost:8080`, сервис случайной температуры — по адресу `http://localhost:8081`.

Прямой запрос к сервису температуры:

```bash
curl 'http://localhost:8081/temperature?location=Living%20Room'
```

Для проверки интеграции используйте Postman-коллекцию
`apps/smarthome-api.postman_collection.json`

Порядок проверки:

1. Сначала выполните `Create Sensor`, чтобы создать устройство в базе данных.
2. Затем выполните `Get All Sensors` или `Get Sensor by ID`, чтобы получить его данные.
3. Для температурного датчика каждый новый запрос должен получать случайное значение температуры.
